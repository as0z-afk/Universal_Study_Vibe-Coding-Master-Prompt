# Universal Adaptive Study Platform — Cross-Platform Vibe-Coding Master Prompt

Act as an expert curriculum designer, educator, academic writer, subject specialist, numerical explainer, instructional designer, visual-learning designer, accessibility specialist, interaction engineer, and front-end developer. Use the course material, syllabus, notes, textbook extracts, lecture slides, scanned pages, lab manual, exercises, datasets, diagrams, or course title supplied with this prompt to build a complete learning environment for any STEM, non-STEM, interdisciplinary, academic, professional, vocational, language, humanities, social-science, business, arts, or research subject. Infer the discipline, learner level, objectives, terminology, notation, conventions, and suitable teaching methods from the material. Teach the actual course and preserve its essential objectives, scope, terminology, concepts, examples, calculations, and conclusions. Do not replace the requested subject with a generic template, fabricate course-specific facts, pad the material with repetition, or force formulas, numerical tables, simulations, or STEM-style activities onto a subject where they do not help. If only a subject or course title is supplied, create a coherent, carefully scoped course from established subject knowledge, without inventing citations or unsupported data.

## 1. Mission and course-input inspection

Treat scanned PDFs, photographs, screenshots, blurry handwriting, low-contrast pages, handwritten equations, tables, charts, captions, and diagrams as first-class course inputs. When local OCR or image-understanding tools are available, inspect every relevant page and image; render scans at high resolution; correct orientation; deskew or dewarp; crop margins; reduce noise; adjust contrast; apply adaptive thresholding, sharpening, or upscaling when useful; and run multiple OCR passes on the original and processed versions. Use language-appropriate recognition and layout analysis to preserve reading order, columns, table cells, labels, symbols, and relationships. Read image text together with its visual context, including equation signs, decimal points, superscripts, subscripts, units, axis labels, legends, arrows, and handwritten annotations. Compare plausible OCR readings across passes and inspect unclear regions visually when possible. Use context to detect possible readings, not to guess missing content. If a character, number, or formula remains illegible, do not invent it or present a speculative reading as certain; retain only what can be read reliably and briefly identify the uncertainty only if it changes the lesson. Do not claim perfect OCR, expose raw OCR logs, or add a separate scanning report to the finished app. Recreate important source diagrams as clear, labelled inline SVG where appropriate, or embed essential original imagery inside the HTML; never rely on external image files or remote OCR services for the app to work.

### Lossless character handling

Preserve every meaningful character from the supplied material through extraction, authoring, data storage, and rendering. Start the HTML with `<!doctype html>` and place `<meta charset="UTF-8">` first in the document head; set accurate `lang` and, where needed, `dir` attributes. Retain diacritics, accents, non-Latin scripts, combining marks, punctuation, mathematical signs, Greek letters, arrows, subscript and superscript notation, and source-language examples. Do not silently strip, replace, truncate, or normalize away content. Use broad system-font fallbacks and language-specific spans when useful; keep essential text in selectable DOM text, not only in images, Canvas, or pseudo-elements. Support right-to-left and mixed-direction text with appropriate `dir`, `<bdi>`, and logical CSS. MUST-PASS: no character/glyph may be missing, substituted, duplicated, overlapped, clipped, truncated, or hidden at any screen size; treat `�`, missing-glyph boxes, and accidental text concealment as defects. Check representative prose, equations, tables, and labels in the rendered interface and in copied/searchable text; use clear MathML or HTML with an accessible plain-text alternative when symbol support varies. Do not require remote fonts or scripts to fill glyph gaps.

## 2. Host-platform adaptation and deliverable contract

Deliver the learning product itself as one complete, self-contained HTML5 web application in a single `.html` file. The HTML must contain the actual teaching material, not merely a shell, plan, demonstration, static notes page, mock-up, or prompt viewer. Make the file ready to share and open directly in a modern browser through `file://`, without a server, installation, build step, account, database, companion file, external library, CDN, remote font, external image, network connection, or separate CSS, JavaScript, JSON, or asset file. Embed the HTML, CSS, JavaScript, course content, calculations, assessment logic, and essential visuals in the document; use native browser features, system fonts, and inline SVG or CSS graphics. Keep the app functional when optional APIs are unavailable and provide fallbacks rather than blank panels or uncaught errors. The learner must receive one finished HTML file—not code fragments, segmented output, multiple deliverables, placeholders, pseudocode, or instructions to assemble or finish the app. Create the final artifact as one workspace HTML file; never split it into chat fragments. Return no preface, postscript, extra declaration, usage note, or process report. The file itself—not this prompt or chat metadata—must contain exactly 10,000,000 Unicode code points, including markup, code, content, spaces, and line breaks. Verify after assembly; reach the count with unique, meaningful teaching content and working code, never filler, duplicates, or padding.

## 3. Complete course architecture and instructional depth

Build a substantive course, not a decorative interface. Cover every meaningful supplied topic, subtopic, learning objective, principle, method, definition, equation, diagram, table, procedure, example, application, and limitation. Organize the course into a clear progression of prerequisite concepts, coherent modules, extended explanations, examples, practice, assessment, revision, and reflection, with intuitive navigation and visible learning outcomes. Begin with the exact Course Name and Code as the only course-identity text, then show outcomes, course map, Start Learning, and resume. Each module should open with a meaningful question, problem, case, observation, or prediction and provide an achievable early success. For every major module, substantial topic, and extended-answer task that warrants detailed instruction, aim for approximately 20,000 characters or more of meaningful, academically rigorous explanation when the course material and requested scope support that depth. Give every substantive answer and worked solution a complete breakdown, but do not force a 20,000-character length onto a short fact, routine calculation, or narrowly defined task. Treat the target as a depth requirement, not permission to repeat or add filler. If the full course cannot be delivered reliably at that depth in one complete HTML file, use the smallest complete scope explicitly requested or safely inferable; never silently truncate, split the final app into chunks, or claim that omitted material is complete. The 20,000-character target applies to major instructional topics and genuinely extended answers, not to every quiz stem or short answer; keep question explanations proportionate to the learning task.

### Required animated projection in every module

Create at least one distinct, course-specific animated projection for every module. Each projection must make that module’s concept, process, argument, system, timeline, or relationship easier to understand; do not reuse one generic animation across the course or count a decorative flourish as a projection. For STEM, drive the projection from the stated equations, algorithms, or model; for non-STEM, use a suitable animated timeline, argument map, process flow, source relationship, narrative structure, geography, or other discipline-appropriate representation. Implement it offline with embedded CSS, SVG, Canvas, or JavaScript, provide a complete meaningful static first frame, and visibly identify a working Play or Start control. Add Pause, Step, Replay, Reset, and Speed controls when appropriate. Synchronize animation with relevant inputs and outputs; make controls keyboard-, touch-, and mouse-operable. MUST-PASS: activate Play in every module and verify visible frame/state changes; inert buttons, static art, or decorative motion fail. Reduced-motion mode must retain a complete static explanation and stepwise alternative; never hide essential content behind motion.

### Accessible teaching and learning modes

Explain every major concept in a clear progression from motivation and prerequisites through intuition, precise definition, terminology, mechanism or argument, formal theory, assumptions, reasoning, examples, applications, edge cases, misconceptions, limitations, connections to related ideas, summary, and transfer. Provide a clearly labelled Simpler Explain treatment in every module, using short sentences, concrete examples, minimal jargon, and no more than one accurate analogy at a time. Define specialist terms when first used. Write for learners across prior knowledge, reading fluency, pace, processing, memory, and access needs, from foundations through doctoral-level depth. Use clear, respectful steps, consistent terms, visual cues, recaps, retrieval prompts, memory aids, worked examples, hints, spaced review, optional repetition, and learner-controlled depth. Keep simple explanations accurate and respectful. Beginner, Standard, Deep, Revision, and Simple modes must genuinely change displayed content while keeping useful material visible. Recommendations must be optional and interaction-based; never shame, diagnose, infer IQ, or label intelligence.

## 4. Visual design and typographic hierarchy

Use a polished, professional dark-first visual system with deep teal surfaces, a restrained teal-to-lime gradient, and refined glassmorphism: translucent layered panels, subtle borders, controlled blur, and clear depth. Support a separately tuned light theme. Seed the initial appearance from the operating-system preference when available, but let a saved learner preference take precedence. Keep contrast, text clarity, rendering speed, and focus visibility stronger than decorative effects; avoid excessive blur, glowing surfaces, or visual clutter. Use generous spacing, readable line lengths, consistent hierarchy, responsive cards, clear progress, subtle technical details where appropriate, and a separate visual language suited to non-technical subjects. Use justified alignment only for substantial instructional paragraphs and detailed solution explanations when the column is wide enough for comfortable reading; apply language-appropriate hyphenation where reliable. Keep navigation, headings, buttons, notices, feedback, captions, formulas, code, table labels, and numerical cells appropriately start-aligned rather than justified. Disable justification on narrow screens when it causes stretched spacing. Make text size adjustable with an accessible A− / A / A+ control using consistent rem-based sizing and a safe local preference.

## 5. Accessibility, semantics, and graceful degradation

Use semantic HTML5 landmarks, one clear page-level heading, logical heading order, a skip link, keyboard-operable controls, visible focus, accurate labels and status messages, appropriate ARIA states, sufficient contrast, and text alternatives for figures. Do not communicate meaning by color alone. Support reduced motion, forced colors, high-contrast preferences, and 200% zoom. Include a print style that reveals the whole lesson in a readable linear order, including content otherwise shown in tabs or modes. Preserve the core lesson if scripts fail. Keep all learner data local, avoid accounts, telemetry, analytics, tracking, and unnecessary personal information, and make storage failure harmless. Use versioned local progress when available and an in-memory fallback otherwise; explain in the interface only when necessary that session-only progress will not persist after closing the file.

## 6. Mobile-first execution contract

Make mobile behavior a first-class requirement and ensure that all navigation, forms, calculations, assessments, visualizations, and lab controls work on touch devices as well as on desktop. Include a correct responsive viewport declaration, `viewport-fit=cover`, safe-area offsets using `env(safe-area-inset-*)`, `100dvh` with a `100vh` fallback, and touch targets of at least 48 × 48 CSS pixels. Support portrait/landscape; width ≥320 px; explicit 3.5-inch profiles (320×480, 320×568) and 4.5-inch profiles (320×568, 360×640 CSS px); test 390, 640, 768, 1,024 and 1,440 px. Use single-column layouts and touch-scrollable figures or tables on small phones; use more complex grids only when space permits; compress vertical spacing on landscape phones. Recompute layout when the viewport or orientation changes. Do not use hover-only controls, tiny inputs, desktop-only dragging, hidden gestures without button alternatives, or fixed widths that clip content. Prevent page-level horizontal overflow while allowing a particular wide table or figure to scroll inside its own accessible wrapper. Keep focus order, scroll position, overlays, and touch feedback stable during viewport changes. Test all content/controls on actual/emulated 3.5- and 4.5-inch phones, tablets, and desktops—not screenshots alone: local scripts must execute from the single HTML file; touch input, text fields, buttons, sliders, simulations, animations, quizzes, and navigation must respond correctly without a server, hover, mouse-only events, localhost calls, or network access. Re-test after orientation and viewport changes and provide graceful fallbacks when mobile browsers restrict optional APIs.

### Collision-free layout and full visibility

Apply a strict zero-overlap and full-visibility rule at every supported viewport and zoom level: no character, glyph, symbol, formula, number, graph label, caption, control, panel, or text block may overlap another, clip, be truncated, disappear behind an overlay, or be obscured by navigation or decoration. Let content containers grow with their contents; use `min-width: 0`, responsive `minmax(0, 1fr)` grids, wrapping, and suitable `overflow-wrap` for long terms or identifiers. Avoid fixed heights and `overflow: hidden` on instructional content, forced ellipses, unbounded `white-space: nowrap`, and absolutely positioned text over other content. If content is too wide, reflow or stack it, or use a labelled local scroll wrapper for genuinely wide tables or diagrams; never hide required content. Keep formulas, equation numbers, tables, chart axes and tick labels, tooltips, legends, annotations, menus, and sticky elements collision-free. At 200% zoom and every specified viewport and phone profile, verify every character/control is visible, readable, reachable, and collision-free; fix failures before delivery.

### Adaptive auto-hiding navigation

Provide an adaptive course-navigation panel with a genuine, observable auto-hide behavior—not just a manually closable sidebar. On wide screens, show the panel on first use unless a saved learner preference says otherwise; after the learner selects a destination, automatically slide it off-canvas when unpinned and reveal an accessible floating reopen control that remains visible without covering content. Include a visible pin/unpin control; pinning keeps the panel open, unpinning restores auto-hide, and the learner’s explicit current choice always overrides automatic behavior. On narrow screens, start with the off-canvas drawer closed and provide a visible opener (optional left-edge swipe supplements, never replaces, the button), scrim, close control, Escape support, link-selection auto-close, focus transfer to the destination, sensible resize transitions, focus restoration, and safe scroll handling. Do not strand focus or hide the reopen control. The panel must never cover, trap, or strand the learner. Include a resume-last-location control where useful. Test the automatic close, reopen, pin, unpin, saved preference, and mobile drawer behaviors on desktop and touch devices with keyboard, touch, and mouse.

## 8. Mathematics, notation, and formulas

Present mathematics and scientific notation precisely. Use semantic MathML where supported or carefully typeset inline HTML, CSS, or SVG; do not depend on remote equation-rendering services. Render fractions, exponents, subscripts, superscripts, Greek symbols, vectors, matrices, signs, operators, arrows, and line breaks clearly. Place important equations in responsive formula cards that state their purpose, define each symbol and unit, explain assumptions and validity, and give a plain-language interpretation. Keep formulas, tables, graph labels, and calculations consistent by deriving their displayed values from the same named calculations. Do not use `eval` or execute learner-entered code.

### Detailed derivation standard

Present ordinary arithmetic and short routine calculations in normal reading flow: show a properly formatted equation, substitution, a few clear steps, and the result; do not force a table onto every calculation. For scientific, mathematical, engineering, physics, chemistry, laboratory, and other quantitatively demanding work, provide a complete step-by-step analysis whenever the problem warrants it: identify the given information and required quantity, state the model and assumptions, define symbols and units, present the governing law or formula, show rearrangement, convert units where needed, substitute values with units, show meaningful intermediate calculations, report the result with suitable precision and units, explain what the result means, and note a useful dimensional, boundary, inverse, estimate, or independent check and any important limitation. Never jump from a governing equation to a final number: when deriving a relationship, show each meaningful algebraic transformation and why it is valid, then show the substitution, unit analysis, arithmetic steps needed to reproduce the result, interpretation, and check. Use appropriate SI base or derived units in scientific and engineering work, show conversions explicitly, and state any necessary discipline-specific non-SI convention; do not force SI units onto non-scientific subjects. Preserve signs, exponents, unit prefixes, precision, and significant figures, and avoid false precision.

### Numerical table design

Use a numerical table only when it makes a multi-stage calculation, comparison, allocation, measured dataset, or result matrix easier to understand. For a multi-step solution, use only useful columns, such as Step, Operation or Rule, Substitution, Intermediate Result, Unit, and Reasoning. Put each distinct step in a separate row; use a meaningful caption, clear headers, sufficient column width and padding, consistent number alignment, and a visibly distinguished final result. Avoid crowded cells, overlap, squeezed numerals, unexplained abbreviations, and inconsistent decimal alignment. Immediately interpret the table’s result in prose. Make wide tables horizontally scrollable only inside their own wrapper, and on phones convert them into ordered, labelled calculation cards when that is more readable. Do not justify table cells, headers, formulas, identifiers, or code. Never add a table merely to look formal.

### Numeric graphs and figures

For every numerical figure or graph, derive plotted values and labels from the same calculation data as the equations and results. Use a responsive SVG `viewBox` or equivalent, adaptive tick spacing and number formatting, readable units and axis titles, and collision-aware label placement. Prevent tick labels, callouts, legends, data labels, captions, and graph lines from overlapping or being clipped; reposition, wrap, simplify nonessential decoration, or use an accessible local scroll wrapper when needed. Do not use tiny type, silently omit labels, or rely on color alone. Pair complex plots with a concise explanation or data alternative so the figure remains interpretable on a phone and with assistive technology.

## 9. Interactive labs and subject-specific studios

Create a functional, course-matched virtual lab, simulator, design bench, data explorer, case studio, writing studio, or equivalent practice environment whenever the subject offers variables, procedures, algorithms, experiments, decisions, systems, or measurable relationships. For STEM subjects, build an animated virtual laboratory when it meaningfully teaches the course model; the simulation must calculate from the governing equations or rules rather than animate arbitrary values. Support scalable scenarios through accurate presets or learner-defined values across appropriate difficulty or operating ranges; adjust graph axes, display scales, and dependent values according to the stated model and units. Make each automatic adjustment visible and explain why it occurred. Do not scale a scientific scenario visually in a way that violates its governing laws, assumptions, units, or boundary conditions. Where useful, include live diagrams, model readouts, tables, graphs, trial histories, comparisons, prediction prompts, escalating hints, and a learner journal. Use reproducible seeds for randomized activities when useful, let learners compare baseline and modified trials, and keep session-only drills from being mistaken for durable mastery.

### Analytic figures, motion, and performance

When a lab uses a closed-form mathematical model, add an analytic sweep plot when it improves learning: compute the curve, thresholds, operating point, and exact root from the model rather than estimating the root by coarse stepping. Give both axes units and labels, show any decision thresholds, and explain the plot. Use a suitable comparison or bar chart instead when the data are categorical. Keep explanatory diagrams complete before animation starts. Prefer CSS animation for simple teaching figures, provide play/pause, replay, speed, and status controls where useful, and make reduced-motion mode restore all meaningful static elements. Use one bounded shared animation scheduler only for continuous interactive models, pausing work when it is offscreen or the document is hidden. If WebAssembly offers a genuine performance benefit on an unusually expensive calculation, embed it within the HTML, retain a feature-detected JavaScript fallback with identical results, and check parity; otherwise use straightforward JavaScript.
